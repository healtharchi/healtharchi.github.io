AWS、OpenCodeとBedrockのオープンモデル活用法

AWS が OpenCode を Bedrock 上の Kimi K3 などオープンウェイトモデルで使う手順を公開。Flex 階層は Standard より 50% 安く、global プロファイルは約 10% 安いと説明しています。

何が発表されたか

AWS は 2026-09-23 付の公式ブログで、OpenCode（Go 製のオープンソースのターミナル型 AI コーディングエージェント）を Amazon Bedrock 上のオープンウェイトモデル（重みが公開されたモデル）で使う手順を公開しました。新モデルや料金改定の発表ではなく、構成と費用の考え方の解説です。

  • 使うモデル: Moonshot AI Kimi K3、OpenAI GPT-OSS 120B、NVIDIA Nemotron 3 Super 120B の 3 つ。
  • 役割分担: プロジェクト直下の opencode.json で、計画（plan）に Kimi K3、実装（build）に Nemotron 3 Super 120B、既定に GPT-OSS 120B を割り当てる例を示しています。
  • Kimi K3: 1M トークンのコンテキストに対応し、reasoning_config（low / high / max）で推論の深さを選べます。
  • 料金階層: Priority・Standard（トークン従量）・Flex の 3 つ。Flex は Standard より 50% 低いコストです。
  • 推論プロファイル: global.moonshotai.kimi-k3 は世界の対応リージョンに振り分け、地理プロファイルより約 10% 安いとしています。us.moonshotai.kimi-k3 は処理を US 内にとどめます。
  • 既定の上限: 毎分 100M トークン、毎分 10K リクエスト。
  • データの扱い: Bedrock は入力・出力を基盤モデルの学習に使わないと明記しています。

具体的なトークン単価は出典に記載なしです。

誰に関係するか

  • 開発者: 席単位の課金ではなく、使った分だけ払うコーディングエージェントを検討している人に関係します。計画と実装でモデルを分ける設定例がそのまま参考になります。
  • 企業のIT部門: データ所在の要件がある場合、global と us のどちらのプロファイルを使うかが費用と要件の分かれ目になります。IAM でモデルを限定する例も示されています。
  • 一般利用者: 影響は小さいです。

費用の目安（自サイトの計算）: 出典の「Flex は Standard より 50% 低い」に従うと、遅延を許容できるバッチ処理の費用は、Flex では Standard の半額になる計算です。Flex と global プロファイルの割引を併用できるかは出典に記載なしです。

今日できること

  • Amazon Bedrock コンソールで、Kimi K3・GPT-OSS 120B・NVIDIA Nemotron 3 Super 120B のモデルアクセスを許可する。
  • データ所在の要件を確認し、global.moonshotai.kimi-k3（約 10% 安い）と us.moonshotai.kimi-k3（US 内で処理）のどちらを使うか決める。
  • テスト生成や一括リファクタリングなど急がない処理を Flex 階層で実行し、Standard との費用差を確かめる。
  • IAM ポリシーで bedrock:InvokeModel などの対象モデルを限定し、使えるモデルを絞る。

注意点

  • 日本リージョンでの提供状況は出典に記載なしです。出典は、対象リージョンでモデルが使えるかを確認するよう述べています。
  • 出典内のベンチマークや他社の数値は企業・第三者の主張で、本記事では性能の優劣を判断していません。
  • 料金の割合（50%、約 10%）は 2026-09-23 公開の出典に記載の時点の説明です。
