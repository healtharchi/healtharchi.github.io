2. Optimizing cost and latency with Amazon Bedrock prompt caching

Amazon Web Services（2026-09-15） ／ 判定: △ 様子見 ／ 重要度 3/5 ／ 提供: 不明・日本: 不明

AWS の Machine Learning Blog が、Amazon Bedrock のプロンプトキャッシュを使って入力トークン費用と初回応答までの時間を下げる方法を解説した。Converse API の cachePoint マーカーの置き方を 6 つの場面（長文ドキュメント、システムプロンプト、ツール定義、TTL の使い分け、テナント分離、LangChain 連携）に分けて示し、キャッシュ書き込み・読み出しの課金区分も表で説明している。

  • 提供条件: 前提として「Amazon Bedrock が使えるサポート対象リージョン（us-west-2 など）の AWS アカウント」と対象モデルのモデルアクセス有効化、Python 3.10 以降が挙げられている。提供段階（GA かどうか）や日本のリージョンについては出典に記載なし。
  • 料金: 標準の入力・出力トークンに加えて 2 つのトークン区分が課金対象になる。cacheWriteInputTokens（初回の書き込み）は標準入力より 25% 高く、cacheReadInputTokens（2 回目以降の読み出し）は 90% 安い。1 時間 TTL での書き込みは標準入力の 2 倍（100% 高い）。具体的な単価は Amazon Bedrock の料金ページを参照とされ、金額の記載はない。
  • 関係する人: 開発者、企業のIT部門、AI サービスのコストを管理する担当者
  • 今日できること: 同じ文書やシステムプロンプトを繰り返し送っている処理を洗い出し、Converse API のリクエストで静的な部分と可変の質問の間に cachePoint を置く ／ 応答の usage に含まれる cacheWriteInputTokens と cacheReadInputTokens を確認し、キャッシュが実際にヒットしているか測る ／ 使うモデルの最小トークン数（Claude Sonnet 4.5 / 4.6 は 1,024、Opus 系は 4,096）を満たしているか確認する ／ TTL の既定が 5 分であることを踏まえ、リクエスト間隔が空く処理では期限切れによる書き込み再発生を見込む
  • 出典: https://aws.amazon.com/blogs/machine-learning/optimizing-cost-and-latency-with-amazon-bedrock-prompt-caching/
